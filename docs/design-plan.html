실습 채점 시스템 설계 계획서

지금 도구는 학생 코드를 받아와 돌려 보고 눈으로 확인하는 데까지 잘 작동합니다. 여기서 점수와 근거까지 나아가려면 한 가지가 먼저 필요합니다. 시스템이 "문제"를 알아야 합니다. 이 문서는 문제 명세를 중심에 두고 나머지 기능을 그 위에 올리는 순서를 정합니다.

목표

이 시스템이 해야 하는 네 가지

기존 목표를 그대로 두고 달성 여부를 판정할 수 있게 다시 적었습니다. 오른쪽은 현재 상태입니다.

G1

제출물 수집

수강생 명단으로 학생 저장소를 일괄 받아오고, 각 학생의 제출 시각과 실패 사유를 남긴다.

대체로 됨
G2

점수 자동 산출

문제별 배점과 케이스별 배점에 따라 학생마다 점수를 계산하고, 분반 전체 성적표를 내보낸다.

미착수
G3

판정 근거 기록

어떤 문제를 어떤 환경에서 어떤 케이스로 채점해 그 점수가 나왔는지, 재채점으로 같은 결과가 나올 만큼 남긴다. 이의제기에 이 기록만으로 답할 수 있어야 한다.

미착수
G4

문제를 시스템 안에 두기

지금 실습 자료에만 있는 문제 정의를 시스템이 읽을 수 있는 형태로 옮겨, 제출 파일명과 배점과 채점 방식이 문제와 함께 관리되게 한다.

미착수
G5

수동 채점

자동 판정을 조교가 덮어쓰고 그 이유를 남긴다. 수동 점수도 자동 점수와 같은 성적표에 들어간다.

실행만 됨
핵심 설계 결정

문제를 일급 개체로 만든다

지금은 "문제"가 학생이 만든 폴더 이름입니다

도구는 과제가 무엇인지 모릅니다. 학생 폴더를 훑어 그 이름으로 정답 경로를 거꾸로 조립하고, 폴더 안에서 main.py 또는 main.c를 찾습니다. 배점을 적을 자리도, 제출 파일명을 규정할 자리도, 지문을 둘 자리도 없습니다.

G2, G3, G4가 모두 이 한 가지 결핍에서 막혀 있습니다. 배점을 적을 곳이 없으니 점수를 계산할 수 없고, 판정 대상을 식별할 수 없으니 근거를 기록할 대상이 정의되지 않고, 문제를 담을 그릇이 없으니 실습 자료를 시스템에 넣을 수 없습니다. 채점 정확성 문제도 같은 뿌리입니다. 제출 파일명을 규정할 수 없어 절반 이상의 제출물을 놓치고, 학생 폴더명이 다르면 매핑할 방법이 없습니다.

따라서 문제 명세를 파일로 정의하고, 채점은 그 명세를 따라 실행하는 구조로 바꿉니다. 명세가 단일 원본이 되고, 테스트케이스와 배점과 실행 조건이 그 아래 모입니다.

데이터 모델

세 개의 파일 계약

명세, 매핑, 기록 세 가지만 정하면 나머지 기능은 이 위에서 조립됩니다. 형식은 사람이 편집기로 고칠 수 있게 YAML을 쓰고, 기계가 남기는 기록은 JSON을 씁니다.

문제 명세

assignments/<과목>/<연도>/<챕터>/<문제>/problem.yaml

한 문제에 대해 알아야 할 전부를 담습니다. 조교가 문제를 만들 때 이 파일부터 쓰고, 채점기는 이 파일만 보고 동작합니다. 

id: system-2025-chap4-prob1
title: 명령행 인자로 받은 파일 복사하기
statement: |
  실습 4-1. argv[1]의 파일을 argv[2]로 복사한다.
  open, read, write 시스템 콜만 사용한다.
source: slides/system-2025-chap4.pptx#p12   # 지문 원본 위치

submit:
  language: c
  files: [main.c, copy.c, prob1.c]     # 허용 파일명, 앞이 우선
  entry: main.c                        # 링크 대상. 생략하면 폴더 전체

build:
  flags: [-Wall, -lm]                   # 지금은 줄 방법이 없는 값

run:
  timeout_sec: 10
  compare: trimmed                      # exact | trimmed | tokens | numeric
  tolerance: 1e-6                       # numeric 일 때만

scoring:
  total: 10
  cases:
    01-basic: 5
    02-empty-file: 3
    03-missing-arg: 2
  manual_override: allowed

due: 2026-10-15T23:59:00+09:00           # 없으면 기한 판정 생략

케이스는 명세 옆에 둡니다. 지금의 세 파일 규약을 그대로 쓰되 이름만 분명히 합니다. 

assignments/system/2025/chap4/prob1/
  problem.yaml
  cases/
    01-basic/
      args.txt          # 명령행 인자. 줄 단위로 하나씩
      stdin.txt         # 표준 입력. 없으면 생략
      expected.txt      # 기대 출력
      files/            # 실행 전 작업 사본에 넣을 입력 파일
        source.txt
    02-empty-file/
    03-missing-arg/

제출물 매핑

assignments/<과목>/<연도>/layout.yaml

학생이 폴더를 어디에 어떤 이름으로 만들었는지는 통제할 수 없습니다. 표준 후보를 여러 개 두고, 그래도 못 찾으면 화면에서 학생별로 한 번 지정하고 그 결과를 이 파일에 저장합니다. 한 번 지정하면 다음 채점부터 자동으로 맞습니다. 

candidates:                  # 모든 학생에게 순서대로 시도
  chap4/prob1:
    - chap4/prob1
    - chap4/hw1
    - chap04/prob1
    - chapter4/prob1

overrides:                   # 화면에서 지정하면 여기에 쌓임
  20xxxxx:
    chap4/prob1: 과제4/1번

실행 폴더에는 학생별 파일과 함께 분반 성적표 summary.csv를 둡니다. 학번, 자동 점수, 최종 점수, 통과 케이스 수, 채점 시각, 실행 환경 순서면 그대로 성적 입력에 쓸 수 있습니다.

채점 흐름

일곱 단계로 재구성

지금 흐름과 크게 다른 지점은 두 곳입니다. 문제 명세가 시작점이 되고, 실행이 학생 저장소가 아니라 작업 사본에서 일어납니다.

1

명세 적재

문제 명세를 읽고 검증합니다. 배점 합이 총점과 맞는지, 케이스 폴더가 실제로 있는지, 기대 출력 파일이 있는지 확인하고 어긋나면 채점을 시작하지 않습니다.

해결: 빈 케이스 폴더로 조용히 통과하는 문제, 배점 부재
2

제출물 확정

학생별로 후보 경로를 순서대로 시도해 제출 폴더를 찾고, 명세의 허용 파일명 중 실제로 있는 것을 고릅니다. 못 찾은 학생은 실패가 아니라 미확정으로 분류해 화면에서 지정하게 합니다.

해결: main 이름만 찾는 문제, 첫 학생 폴더명 강제, 경로 잔존
3

작업 사본 생성

확정된 제출 파일과 케이스 입력 파일을 임시 작업 폴더로 복사합니다. 학생 저장소는 이후 단계에서 읽지도 쓰지도 않습니다.

해결: 제출물 훼손, 산출물 잔존, 심볼릭 링크 추종, 재채점 결과 불일치
4

빌드

명세의 대상 파일과 컴파일 옵션으로 빌드합니다. 제한 시간을 걸고, 실패하면 컴파일러 메시지를 그대로 기록에 남깁니다. 실행 환경 판정은 한 곳에서만 합니다.

해결: 옵션 지정 불가, 폴더 전체 링크, 컴파일 무제한 대기, 모드 판정 중복
5

케이스 실행

케이스마다 인자와 표준 입력을 주고 제한 시간 안에 실행합니다. 시간 초과 시 컨테이너 안의 프로세스까지 확실히 정리하고, 출력 기록량에 상한을 둡니다.

해결: 좀비 프로세스, 디스크 고갈, 원인 불명 오류 보고
6

비교와 점수 산출

명세가 지정한 비교 방식으로 판정하고 케이스 배점을 더해 자동 점수를 냅니다. 실패한 케이스는 차이나는 첫 줄을 함께 남깁니다.

해결: 단일 비교 규칙, 점수 개념 부재, 출력만 보여주는 리포트
7

기록과 성적표

학생별 기록 파일과 분반 성적표를 씁니다. 이 단계가 끝나야 채점이 완료된 것으로 봅니다. 화면 표시는 기록 파일을 읽어 보여주는 것으로 바꿉니다.

해결: 결과 영속화 부재, 예외 한 번에 기록 소실, 성적표 수단 없음
모듈 구조

역할 하나에 파일 하나

지금 evaluator.py 하나가 명단 파싱, 저장소 동기화, 폴더 탐색, 파일 조작, 채점 지휘, 로그 서식까지 여섯 가지를 맡고 있습니다. 새 기능을 여기에 더 넣으면 손댈 수 없게 됩니다. 화면에 의존하지 않는 부분을 먼저 떼어내면 테스트를 붙일 수 있습니다.

제안 모듈역할현재 위치
core/roster.py명단 읽기와 검증. 형식 오류를 예외 대신 결과로 반환evaluator.py 일부
core/sync.py저장소 수집. 실패 분류, 빈 폴더 정리, 커밋 시각 수집gitmanager.py
core/manifest.py문제 명세 적재와 검증신규
core/resolver.py학생 제출물 경로와 파일 확정신규
core/workspace.py작업 사본 생성과 정리신규
core/runner.py환경별 빌드와 실행. 모드 판정의 유일한 장소grader.py 전반부
core/compare.py비교 전략 네 가지grader.py:215
core/scorer.py케이스 배점 합산과 수동 조정 반영신규
core/record.py기록 파일과 성적표 읽기 쓰기신규
ui/화면. 도메인 계층은 서식 없는 자료만 반환gui.py

기존 grader.py는 이미 화면에 의존하지 않아 그대로 옮기기 쉽습니다. 이번 감사에서 화면 없이 불러 동작을 확인할 수 있었던 것도 그 덕입니다. 데이터베이스 계층 세 파일은 2023년 이후 연결된 적이 없고 기록을 파일로 남기기로 했으니, 지우거나 별도 폴더로 보관합니다.

실행 계획

여섯 단계, 각 단계의 완료 기준

순서에 이유가 있습니다. 채점 대상을 정확히 고르는 문제를 닫기 전에 점수 계산을 올리면 틀린 점수가 자동으로 기록됩니다. 안전 조치를 먼저 하고, 정확성을 세운 다음 점수와 기록을 올립니다.

M0

안전 조치

설계 변경 없음
  • 개인정보 분리. 명단과 데이터베이스 파일을 추적에서 빼고 무시 규칙을 추가합니다. 원격 이력 정리는 별도로 판단합니다.
  • 파일 로그 활성화. 주석 처리된 파일 기록을 켜서 최소한 콘솔을 닫아도 흔적이 남게 합니다.
  • 즉시 고칠 결함. 파일 추가 기능의 미import, 수동 실행의 환경 판정 누락, 설정값 없는 호출 경로.
완료 기준 새 커밋에 개인정보가 들어가지 않고, 세 결함이 재현되지 않는다.
M1

문제 명세 도입

G4의 토대
  • 명세 형식 확정과 적재기. manifest.py와 검증 규칙.
  • 기존 케이스 이관. 현재 testcase 아래 다섯 문제를 새 구조로 옮기고 배점을 채웁니다.
  • 제출물 확정기. 후보 경로와 허용 파일명으로 매핑하고, 미확정 학생을 화면에서 지정해 저장합니다.
  • 실제 한 문제로 검증. 2025년 3분반의 한 챕터를 명세로 정의해 30명 전원이 확정되는지 봅니다.
완료 기준 한 문제에 대해 분반 전원의 제출 파일이 확정되고, 미확정은 이유와 함께 목록으로 나온다.
M2

작업 사본과 실행 정리

정확성
  • 작업 사본 도입. 채점이 학생 저장소를 건드리지 않게 합니다.
  • 빌드 분리. 명세의 대상 파일과 옵션을 쓰고 컴파일에 제한 시간을 겁니다.
  • 실행 환경 일원화. 세 곳에 흩어진 모드 판정을 하나로 모으고 컨테이너 가동 여부를 먼저 확인합니다.
  • 정리 보장. 시간 초과 시 컨테이너 내부 프로세스까지 종료하고 출력 기록량에 상한을 둡니다.
완료 기준 같은 문제를 두 번 채점해도 결과가 같고, 학생 저장소 상태가 채점 전과 동일하다.
M3

점수 산출과 기록

G2, G3
  • 비교 전략 네 가지. 완전일치, 공백 정리, 토큰 단위, 수치 허용오차.
  • 점수 산출기. 케이스 배점 합산과 총점 검증.

  • 예외 경계. 채점 루프와 명단 읽기에 경계를 두어 한 학생의 실패가 배치를 멈추지 않게 합니다.

범위 밖

이번에 하지 않을 것

  • 실습 자료 자동 파싱. 슬라이드에서 문제를 추출하지 않습니다. 명세에 지문을 적고 원본 위치를 링크로 남기는 편이 유지됩니다. 반대로 명세에서 자료를 생성하는 방향은 나중에 검토할 수 있습니다.
  • 표절과 유사도 검사. 별도 도구의 영역입니다. 다만 기록에 커밋 해시를 남겨 두면 나중에 붙이기 쉬워집니다.
  • 웹 서비스화와 다중 사용자. 당장은 조교 한 명이 자기 PC에서 돌리는 도구로 유지합니다. 기록을 파일로 남기기로 한 이유이기도 합니다.
  • 학생용 화면. 학생이 스스로 채점을 돌려보는 기능은 격리 요건이 완전히 달라집니다.

배점을 케이스 단위로 줄지, 문제 단위로만 줄지

케이스별 배점을 기본으로 두었습니다. 부분점수를 주려면 케이스 단위가 필요하고, 문제 단위만 원하면 케이스 배점을 생략하고 전부 통과일 때만 만점으로 처리하면 됩니다.

기존 테스트케이스와 폴더 구조를 바꿔도 되는지

새 구조로 옮기는 것을 전제로 썼습니다. 기존 다섯 문제뿐이라 이관 부담은 작습니다. 옛 구조를 함께 읽는 호환 코드는 두지 않는 편을 권합니다. 지금 규약이 세 갈래로 갈린 원인이 그 호환 코드였습니다.

실행 환경을 문제 명세가 정할지, 조교가 그때그때 고를지

명세에 두지 않고 실행 시 선택으로 남겼습니다. 다만 기록에 어떤 환경이었는지 반드시 남깁니다. 같은 코드가 환경에 따라 다르게 채점되는 문제는 컴파일 옵션을 명세로 옮기면 대부분 사라집니다.

개인정보 이력 정리를 어디까지 할지

M0에서는 추적 중단까지만 넣었습니다. 이미 원격에 올라간 이력을 다시 쓰는 일은 공유 저장소라 되돌리기 어려우니 별도로 결정하시는 편이 좋습니다.

파일을 택했습니다. 조교가 직접 열어볼 수 있고 git으로 이력이 남고 성적 입력에 바로 쓸 수 있습니다. 2023년에 만든 데이터베이스 계층은 정리 대상으로 보았습니다. 나중에 학기 간 통계가 필요해지면 기록 파일을 읽어 적재하는 쪽이 낫습니다.
