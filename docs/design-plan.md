- 작성일: 2026-09-11
- 기준 커밋: `e6f13ff` (브랜치 `GEN-850_evaluation`)
- 웹 버전: https://claude.ai/code/artifact/8007ed34-4a32-49d7-b51a-c49e36960dc9
- 함께 보기: [현재 상태 감사 보고서](audit-report.md)

지금 도구는 학생 코드를 받아와 돌려 보고 눈으로 확인하는 데까지 잘 작동한다.
여기서 점수와 근거까지 나아가려면 한 가지가 먼저 필요하다. **시스템이 "문제"를 알아야 한다.**
이 문서는 문제 명세를 중심에 두고 나머지 기능을 그 위에 올리는 순서를 정한다.

## 1. 목표

기존 목표를 그대로 두고 달성 여부를 판정할 수 있게 다시 적었다.

| ID | 목표 | 정의 | 현재 |
|----|------|------|------|
| G1 | 제출물 수집 | 명단으로 학생 저장소를 일괄 수집하고, 제출 시각과 실패 사유를 남긴다 | 대체로 됨 |
| G2 | 점수 자동 산출 | 문제별·케이스별 배점으로 학생 점수를 계산하고 분반 성적표를 내보낸다 | 미착수 |
| G3 | 판정 근거 기록 | 어떤 문제를 어떤 환경에서 어떤 케이스로 채점해 그 점수가 나왔는지 재현 가능하게 남긴다 | 미착수 |
| G4 | 문제를 시스템 안에 두기 | 실습 자료에만 있는 문제 정의를 시스템이 읽을 형태로 옮긴다 | 미착수 |
| G5 | 수동 채점 | 자동 판정을 덮어쓰고 이유를 남긴다. 수동 점수도 같은 성적표에 들어간다 | 실행만 됨 |

## 2. 핵심 설계 결정: 문제를 일급 개체로 만든다

### 지금은 "문제"가 학생이 만든 폴더 이름이다

도구는 과제가 무엇인지 모른다. 학생 폴더를 훑어 그 이름으로 정답 경로를 거꾸로 조립하고,
폴더 안에서 `main.py` 또는 `main.c`를 찾는다. 배점을 적을 자리도, 제출 파일명을 규정할 자리도,
지문을 둘 자리도 없다.

### G2, G3, G4가 모두 이 하나의 결핍에서 막혀 있다

- 배점을 적을 곳이 없으니 점수를 계산할 수 없다
- 판정 대상을 식별할 수 없으니 근거를 기록할 대상이 정의되지 않는다
- 문제를 담을 그릇이 없으니 실습 자료를 시스템에 넣을 수 없다

채점 정확성 문제도 같은 뿌리다. 제출 파일명을 규정할 수 없어 절반 이상의 제출물을 놓치고,
학생 폴더명이 다르면 매핑할 방법이 없다.

**따라서 문제 명세를 파일로 정의하고, 채점은 그 명세를 따라 실행하는 구조로 바꾼다.**

## 3. 데이터 모델: 세 개의 파일 계약

명세, 매핑, 기록 세 가지만 정하면 나머지 기능은 이 위에서 조립된다.
사람이 편집기로 고치는 것은 YAML, 기계가 남기는 기록은 JSON을 쓴다.

### 3.1 문제 명세

위치: `assignments/<과목>/<연도>/<챕터>/<문제>/problem.yaml`

```yaml
id: system-2025-chap4-prob1
title: 명령행 인자로 받은 파일 복사하기
statement: |
  실습 4-1. argv[1]의 파일을 argv[2]로 복사한다.
  open, read, write 시스템 콜만 사용한다.
source: slides/system-2025-chap4.pptx#p12   # 지문 원본 위치

submit:
  language: c
  files: [main.c, copy.c, prob1.c]     # 허용 파일명, 앞이 우선
  entry: main.c                        # 링크 대상. 생략하면 폴더 전체

build:
  flags: [-Wall, -lm]                  # 지금은 줄 방법이 없는 값

run:
  timeout_sec: 10
  compare: trimmed                     # exact | trimmed | tokens | numeric
  tolerance: 1e-6                      # numeric 일 때만

scoring:
  total: 10
  cases:
    01-basic: 5
    02-empty-file: 3
    03-missing-arg: 2
  manual_override: allowed

due: 2026-10-15T23:59:00+09:00         # 없으면 기한 판정 생략
```

케이스는 명세 옆에 둔다. 현재 세 파일 규약을 그대로 쓰되 이름만 분명히 한다.

```
assignments/system/2025/chap4/prob1/
  problem.yaml
  cases/
    01-basic/
      args.txt          # 명령행 인자
      stdin.txt         # 표준 입력. 없으면 생략
      expected.txt      # 기대 출력
      files/            # 실행 전 작업 사본에 넣을 입력 파일
        source.txt
    02-empty-file/
    03-missing-arg/
```

### 3.2 제출물 매핑

위치: `assignments/<과목>/<연도>/layout.yaml`

학생이 폴더를 어디에 어떤 이름으로 만들었는지는 통제할 수 없다.
표준 후보를 여러 개 두고, 못 찾으면 화면에서 학생별로 한 번 지정하고 그 결과를 저장한다.
한 번 지정하면 다음 채점부터 자동으로 맞는다.

```yaml
candidates:                  # 모든 학생에게 순서대로 시도
  chap4/prob1:
    - chap4/prob1
    - chap4/hw1
    - chap04/prob1
    - chapter4/prob1

overrides:                   # 화면에서 지정하면 여기에 쌓임
  20xxxxx:
    chap4/prob1: 과제4/1번
```

### 3.3 채점 기록

위치: `records/<연도>/<분반>/<문제>/<실행ID>/`

G3의 핵심이다. 채점 한 번을 하나의 실행으로 보고, 그 실행의 조건과 학생별 결과를 함께 남긴다.
조건을 같이 남기는 이유는 재채점 결과가 달라졌을 때 무엇이 달라졌는지 가려내기 위해서다.

```json
{
  "student_id": "20xxxxx",
  "problem_id": "system-2025-chap4-prob1",
  "graded_at": "2026-10-16T14:30:22+09:00",

  "tool_commit": "e6f13ff",
  "manifest_sha": "sha256:9c1f...",
  "env": { "mode": "docker", "image": "grader-image:latest",
           "compiler": "gcc 11.4.0" },

  "submission": {
    "resolved_path": "chap4/prob1",
    "matched_file": "main.c",
    "commit": "a3f9c21",
    "committed_at": "2026-10-14T21:03:11+09:00",
    "late_hours": 0
  },

  "cases": [
    { "name": "01-basic", "passed": true,
      "points": 5, "max": 5,
      "exit_code": 0, "duration_ms": 118,
      "stdout": "...", "expected": "...", "diff": null },
    { "name": "03-missing-arg", "passed": false,
      "points": 0, "max": 2,
      "exit_code": 139, "failure": "segfault",
      "stdout": "", "expected": "usage: copy src dst" }
  ],

  "auto_score": 8,
  "final_score": 9,
  "override": {
    "by": "조교",
    "reason": "인자 검사 누락이나 복사 로직은 정상. 부분 인정",
    "at": "2026-10-16T15:02:40+09:00"
  }
}
```

실행 폴더에는 학생별 파일과 함께 분반 성적표 `summary.csv`를 둔다.
학번, 자동 점수, 최종 점수, 통과 케이스 수, 채점 시각, 실행 환경 순서면 성적 입력에 바로 쓸 수 있다.

## 4. 채점 흐름: 일곱 단계

지금 흐름과 크게 다른 지점은 두 곳이다. 명세가 시작점이 되고, 실행이 학생 저장소가 아니라
작업 사본에서 일어난다.

| # | 단계 | 내용 | 해결되는 결함 |
|---|------|------|--------------|
| 1 | 명세 적재 | 배점 합, 케이스 폴더 존재, 기대 출력 확인 후 시작 | 빈 케이스 폴더 통과, 배점 부재 |
| 2 | 제출물 확정 | 후보 경로 순회, 허용 파일명 매칭, 미확정은 별도 분류 | F06, F13, F10 |
| 3 | 작업 사본 생성 | 제출 파일과 케이스 입력을 임시 폴더로 복사 | F05, F33, F41 |
| 4 | 빌드 | 명세의 대상 파일과 옵션 사용, 제한 시간 부여 | A2, F07, F53, F11 |
| 5 | 케이스 실행 | 인자·표준입력 주입, 초과 시 컨테이너 내부까지 정리 | F09, A3, F24 |
| 6 | 비교와 점수 산출 | 명세의 비교 방식으로 판정 후 배점 합산 | F48, G2 |
| 7 | 기록과 성적표 | 학생별 기록과 분반 성적표 기록. 이 단계까지 끝나야 완료 | A1, G3 |

## 5. 모듈 구조

지금 `evaluator.py` 하나가 명단 파싱, 저장소 동기화, 폴더 탐색, 파일 조작, 채점 지휘,
로그 서식까지 여섯 가지를 맡고 있다. 화면에 의존하지 않는 부분을 먼저 떼어내면 테스트를 붙일 수 있다.

| 제안 모듈 | 역할 | 현재 위치 |
|-----------|------|-----------|
| `core/roster.py` | 명단 읽기와 검증. 형식 오류를 예외 대신 결과로 반환 | `evaluator.py` 일부 |
| `core/sync.py` | 저장소 수집. 실패 분류, 빈 폴더 정리, 커밋 시각 수집 | `gitmanager.py` |
| `core/manifest.py` | 문제 명세 적재와 검증 | 신규 |
| `core/resolver.py` | 학생 제출물 경로와 파일 확정 | 신규 |
| `core/workspace.py` | 작업 사본 생성과 정리 | 신규 |
| `core/runner.py` | 환경별 빌드와 실행. 모드 판정의 유일한 장소 | `grader.py` 전반부 |
| `core/compare.py` | 비교 전략 네 가지 | `grader.py:215` |
| `core/scorer.py` | 케이스 배점 합산과 수동 조정 반영 | 신규 |
| `core/record.py` | 기록 파일과 성적표 읽기 쓰기 | 신규 |
| `ui/` | 화면. 도메인 계층은 서식 없는 자료만 반환 | `gui.py` |

`grader.py`는 이미 화면에 의존하지 않아 그대로 옮기기 쉽다.
데이터베이스 계층 세 파일은 2023년 이후 연결된 적이 없고 기록을 파일로 남기기로 했으니
지우거나 별도 폴더로 보관한다.

## 6. 실행 계획

순서에 이유가 있다. 채점 대상을 정확히 고르는 문제를 닫기 전에 점수 계산을 올리면
틀린 점수가 자동으로 기록된다.

### M0 · 안전 조치

- 개인정보 분리. 명단과 데이터베이스 파일을 추적에서 빼고 무시 규칙 추가
- 파일 로그 활성화
- 즉시 고칠 결함: 파일 추가 기능의 미import(F18), 수동 실행 환경 판정 누락(F11), 설정값 없는 호출(F25)

**완료 기준** 새 커밋에 개인정보가 들어가지 않고, 세 결함이 재현되지 않는다.

### M1 · 문제 명세 도입

- 명세 형식 확정과 적재기
- 기존 케이스 이관. 현재 `testcase` 아래 다섯 문제를 새 구조로 옮기고 배점을 채움
- 제출물 확정기. 후보 경로와 허용 파일명으로 매핑, 미확정 학생은 화면에서 지정해 저장
- 실제 한 문제로 검증. 2025년 3분반 한 챕터를 명세로 정의해 30명 전원 확정되는지 확인

**완료 기준** 한 문제에 대해 분반 전원의 제출 파일이 확정되고, 미확정은 이유와 함께 목록으로 나온다.

### M2 · 작업 사본과 실행 정리

- 작업 사본 도입. 채점이 학생 저장소를 건드리지 않게 함
- 빌드 분리. 명세의 대상 파일과 옵션 사용, 컴파일에 제한 시간
- 실행 환경 일원화. 세 곳의 모드 판정을 하나로, 컨테이너 가동 여부 사전 확인
- 정리 보장. 시간 초과 시 컨테이너 내부 프로세스 종료, 출력 기록량 상한

**완료 기준** 같은 문제를 두 번 채점해도 결과가 같고, 학생 저장소 상태가 채점 전과 동일하다.

### M3 · 점수 산출과 기록

- 비교 전략 네 가지: 완전일치, 공백 정리, 토큰 단위, 수치 허용오차
- 점수 산출기. 케이스 배점 합산과 총점 검증
- 기록 저장. 학생별 기록 파일과 분반 성적표. 이미 발신 중인 `grade_finished` 신호를 받는 쪽 구현
- 예외 경계. 한 학생의 실패가 배치를 멈추지 않게 함

**완료 기준** 분반 한 문제를 채점하면 성적표 파일이 나오고, 기록만 보고 각 점수의 이유를 설명할 수 있다.

### M4 · 수동 채점 통합

- 판정 덮어쓰기. 자동 점수 옆에 최종 점수와 이유를 입력해 같은 기록에 저장
- 수동 실행을 기록과 연결
- 채점 화면 개편. 서식 로그 대신 기록을 읽어 표로 표시, 학생 출력은 이스케이프

**완료 기준** 수동 조정한 점수가 성적표에 반영되고 조정 이유가 기록에 남는다.

### M5 · 운영 기능과 테스트

- 골든 테스트. 가짜 저장소와 가짜 명세로 파이프라인 전체 검증. 네 환경의 결과 일치 확인
- 제출 기한 판정. 수집 때 커밋 시각을 읽어 지연 여부 기록
- 채점 비동기화와 진행 표시
- 문서. 실행 요건, 작업 디렉터리, 컨테이너 준비, 명세 작성법

**완료 기준** 테스트가 통과한 상태로 한 학기 분량을 채점할 수 있고, 새 조교가 문서만 보고 채점을 돌릴 수 있다.

## 7. 범위 밖

- **실습 자료 자동 파싱.** 슬라이드에서 문제를 추출하지 않는다. 명세에 지문을 적고 원본 위치를
  링크로 남기는 편이 유지된다. 반대로 명세에서 자료를 생성하는 방향은 나중에 검토할 수 있다.
- **표절과 유사도 검사.** 별도 도구의 영역이다. 기록에 커밋 해시를 남겨 두면 나중에 붙이기 쉬워진다.
- **웹 서비스화와 다중 사용자.** 조교 한 명이 자기 PC에서 돌리는 도구로 유지한다.
  기록을 파일로 남기기로 한 이유이기도 하다.
- **학생용 화면.** 학생이 스스로 채점을 돌려보는 기능은 격리 요건이 완전히 달라진다.

다르게 가야 할 것이 있으면 이 절을 고치고 진행한다.
