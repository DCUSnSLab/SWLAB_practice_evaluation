# 실습 자동채점 도구 감사 보고서

- 작성일: 2026-09-10
- 기준 커밋: `e6f13ff` (브랜치 `GEN-850_evaluation`)
- 웹 버전: https://claude.ai/code/artifact/50ce78d0-720c-4a4c-adaa-87867dc2ae79
- 함께 보기: [설계 계획서](design-plan.md)

학생 GitHub 저장소를 일괄 수집해 텍스트 테스트케이스로 자동 채점하는 PyQt6 도구다.
설계 방향은 타당하고 실제로 쓰이며 다듬어지고 있다. 다만 지금 상태에서는
**성적이 학생 코드보다 조교가 누른 실행 모드 라디오와 학생의 폴더 작명에 더 크게 좌우된다.**
자동 결과를 사람이 재확인하는 전제에서만 쓰는 것이 안전하다.

| 지표 | 값 |
|------|-----|
| 자동 채점이 소스를 찾지 못하는 문제 폴더 | 626 / 1,163 (54%) |
| 채점 결과의 파일 기록 | 0건 |
| 채점기 산출물로 오염된 학생 저장소 | 13 / 30 |
| 검증을 통과한 결함 | 73건 (심각 19, 보통 29, 경미 25) |

---

## 1. 무엇을 하는 도구인가

조교가 수강생 명단 CSV를 고르면 학생 저장소를 한꺼번에 받아오고, 학번 폴더를 훑어
과제별로 프로그램을 실행한 뒤 기대 출력과 글자 단위로 비교한다.
애매한 제출물은 수동 실행 탭과 코드 미리보기로 직접 확인한다.

| # | 단계 | 내용 | 위치 |
|---|------|------|------|
| 1 | 수집 | 학번·이름·저장소 주소 세 열을 헤더 없이 읽음. 연도는 CSV 상위 폴더명에서 | `evaluator.py` |
| 2 | 동기화 | 폴더가 있으면 pull, 없으면 clone. 실패해도 로그만 남기고 진행 | `gitmanager.py` |
| 3 | 탐색 | 연도·분반·학생·챕터·문제를 좁혀감. 목록은 학생이 만든 실제 폴더명 | `gui.py` |
| 4 | 실행 | 표준 입력과 인자를 넣고 10초 제한. Windows/WSL/Linux/Docker 중 선택 | `grader.py` |
| 5 | 판정 | 줄바꿈을 맞추고 앞뒤 공백을 떼어 완전 일치 비교. 결과는 화면에만 | `grader.py` |

## 2. 구조

표시, 조회, 실행, 수집이 파일 단위로 분리되어 있고 순환 의존이 없다.
특히 실행기는 화면 요소에 의존하지 않아 화면 없이 단독으로 불러 검증할 수 있다.

| 모듈 | 줄 | 역할 | 상태 |
|------|-----|------|------|
| `main.py` | 7 | 채점 화면 진입점 | 사용 |
| `gui.py` | 741 | 네 개 열 주 화면, 채점 리포트, 수동 실행 탭 | 사용 |
| `evaluator.py` | 343 | 명단 읽기, 폴더 탐색, 파일 조작, 채점 지휘, 로그 서식 | 사용 |
| `grader.py` | 341 | 네 환경별 실행, 테스트케이스 적재, 출력 비교 | 사용 |
| `gitmanager.py` | 50 | 학생 저장소 clone 및 pull | 사용 |
| `lecture.py` / `student.py` | 54 | 강좌·학생 자료 구조, 폴더명 규칙 | 사용 |
| `case_generator.py` | 201 | 정답 코드를 실행해 기대 출력을 만드는 별도 창 | 사용, 주 화면과 미연결 |
| `dbbase.py` / `swlab_db.py` / `chapter.py` | 111 | 2023년에 만든 데이터베이스 계층 | 미연결, 불러오면 실패 |

디렉터리 규약은 네 갈래로 갈라져 있다. 학생 코드는 `src/origin/과목_분반_연도/학번/`,
테스트케이스는 `testcase/과목/챕터/문제/`에 두는데, 케이스 생성기는 결과를
`testdata/폴더명/testcases/…`에 저장하고 그 위치를 읽는 코드는 호출되지 않는다.
즉 생성기로 만든 케이스를 채점기가 기본 경로에서 찾지 못한다.

## 3. 실행 환경: 같은 코드, 네 가지 다른 결과

| 환경 | 파이썬 | C 컴파일 | 산출물 정리 | 실행 위치 |
|------|--------|----------|-------------|-----------|
| Docker (기본값) | `docker exec … python3` | `sh -c "gcc -o main *.c && ./main"` | 없음, 학생 폴더에 남음 | 컨테이너 작업 디렉터리 |
| WSL | `wsl python3 /mnt/c/…` | `wsl bash -c 'gcc -o … *.c'` | 없음, 학생 폴더에 남음 | 지정 안 됨, 상대 경로 파일 못 읽음 |
| Linux | `python3 …` | `gcc -o "…/main" "…"/*.c` 셸 경유 | 실행 후 삭제 | 학생 폴더 |
| Windows | `python …` | `gcc -o "…\main.exe" "…\*.c"` 셸 경유 | 실행 후 삭제 | 학생 폴더 |

네 환경 모두 컴파일 명령이 한 줄로 고정되어 있어 링크 옵션을 줄 수 없고,
지정한 파일 대신 폴더 안의 모든 `.c`를 한꺼번에 링크한다.
실측한 저장소에서 `.c`가 둘 이상인 폴더가 801개이고, 표본 300개 중 230개에서
두 개 이상의 파일이 각자 `main`을 정의하고 있어 중복 정의로 링크가 깨진다.
수동 실행 탭은 Linux 선택을 아예 무시하고 Windows 명령으로 돌린다.

## 4. 채점 신뢰성을 직접 깨는 결함

아래 일곱 건은 학생의 코드가 맞았는지와 무관하게 결과를 바꾼다.
모두 코드를 직접 읽고 실측으로 재현해 확정했다.

### F06 · 파일 이름이 `main`이 아니면 채점 자체가 되지 않는다

자동 채점은 대상 파일을 넘기지 않고 폴더에서 `main.py`와 `main.c`만 찾는다.
없으면 소스를 찾을 수 없다는 실패로 끝나고, 요약에는 0점처럼 남는다.
파이썬 과목 제출물은 대부분 문제 번호를 파일명으로 쓰기 때문에 사실상 전원이 여기에 걸린다.

- 실측: 2025년 3분반 문제 폴더 1,163개 중 626개가 다른 이름의 소스만 보유
- 실측: 파이썬 과목 제출 파일명 상위는 `prob1.py` 142개, `prob2.py` 118개, `prob3.py` 115개, `main.py` 32개

### F10 · 문제 폴더가 없는 챕터에서는 직전 문제의 정답으로 채점한다

테스트케이스 경로는 문제를 고를 때만 갱신된다. 하위 문제 폴더가 없는 챕터로 옮기면
경로 칸이 비워지지 않고 이전 값이 그대로 남으며, 채점 시작 전 검사는 그 경로가 존재하는지만 본다.
결과적으로 다른 문제의 정답과 비교한 판정이 조용히 나온다.
파이썬 과목은 문제 폴더 없이 챕터에 파일을 직접 두는 구조라 상시 해당된다.

- `gui.py:452` 경로 갱신 함수가 문제값이 비면 즉시 반환
- `gui.py:589` 존재 여부만 확인
- 실측: 파이썬 4개 분반 전부 챕터 하위에 문제 폴더 없음

### F13 · 여러 학생을 함께 채점하면 첫 학생의 폴더명이 전원에게 강제된다

챕터와 문제 목록은 선택 목록의 첫 학생 폴더에서만 채워지고, 그 문자열이
선택된 모든 학생에게 그대로 적용된다. 폴더명을 조금 다르게 쓴 학생은
디렉터리를 찾을 수 없다는 실패로 끝난다.

- 실측: 9개 분반 중 8개는 전원 공통 챕터 0개
- 실측: 2025년 3분반 30명 중 `chap3` 보유 24명, 나머지 6명은 실패 처리

### A2 · 컴파일 옵션을 줄 수 없어 정상 코드가 환경에 따라 갈린다

컴파일 명령이 네 환경 모두 한 줄로 굳어 있어 링크할 라이브러리나 표준을 지정할 방법이
화면에도 케이스 형식에도 없다. 리눅스 계열은 수학 함수에 별도 링크를 요구하므로
컨테이너·리눅스·WSL에서는 컴파일이 실패하고 Windows에서는 같은 코드가 통과한다.

- 실측: 프로젝트 Dockerfile로 빌드한 이미지에서 `sqrt` 사용 코드 컴파일 시 undefined reference, `-lm` 추가 시 정상
- 실측: 같은 이미지에 make, g++, pip 없음. Makefile 제출이나 C++ 혼용 과제는 채점 대상이 될 수 없음

### A1 · 결과가 어디에도 저장되지 않고, 예외 한 번에 기록째 사라진다

채점 결과의 유일한 기록은 화면의 텍스트 창이다. 구조화된 결과를 담은 신호는 보내지만
받는 곳이 없고, 파일 로그는 주석 처리되어 꺼져 있으며 데이터베이스 계층은 연결되지 않았다.
성적표를 만들 수단이 없어 화면을 읽어 손으로 옮겨야 하고,
채점 루프에 예외 처리가 없어 한 번의 오류로 배치 전체 기록이 날아간다.

- `evaluator.py:228` 결과 신호를 받는 코드가 전체 소스에 없음
- `setup_logging.py:19` 파일 로그 주석 처리
- `gui.py:608` 채점 루프에 예외 처리 없음
- 실측: 슬롯에서 예외 발생 시 프로세스가 추적 정보 없이 종료

### F05 · 채점이 학생 저장소를 직접 건드려 제출물을 훼손한다

보조 입력 파일을 학생 폴더에 복사한 뒤 채점이 끝나면 같은 이름의 파일을 지운다.
학생이 같은 이름의 파일을 커밋해 두었다면 그 파일이 사라지고,
컨테이너와 WSL에서는 컴파일 산출물이 정리되지 않고 그대로 쌓인다.
다음 동기화에서 충돌이 나고, 재채점 결과가 첫 채점과 달라진다.

- `grader.py:305` 복사, `grader.py:321` 삭제. 둘 다 사전 확인 없음
- 실측: 2025년 3분반 저장소 30개 중 13개가 오염 상태, 잔존 바이너리 2,818개

### F14 · 명단 파일 형식이 조금만 달라도 앱이 그대로 종료된다

명단은 검증 없이 읽는다. 헤더 행이 있거나 빈 줄이 섞이거나 열이 부족하거나
인코딩이 다르면 작업 스레드에서 예외가 나고, 이 경우 화면이 오류를 표시하지 못한 채
프로세스가 끝난다. 파일 경로에 숫자가 없으면 분반 추출에서도 같은 결과가 된다.

- `evaluator.py:58` 열 접근과 정수 변환에 검증 없음
- `gui.py:17` 작업 함수에 예외 처리 없음
- 실측: 네 가지 형식 오류를 실제 작업 스레드에 넣어 재현, 추적 정보 없이 종료

## 5. 데이터 안전

- **학생 개인정보가 저장소 이력에 있다.** 학번·이름·저장소 주소가 담긴 명단 8개와
  sqlite 파일이 2023년 커밋부터 추적되고 있다. 무시 규칙은 clone된 학생 코드만 막고 명단은 막지 않는다.
  아직 커밋되지 않은 2025, 2026 폴더도 규칙이 없어 다음 일괄 추가에 함께 올라간다. (F01)
- **컨테이너 격리가 사실상 없다.** 프로젝트 루트 전체가 읽기 쓰기로 마운트되고 root로 실행되며
  메모리·프로세스 수·네트워크 제한이 없다. 학생 코드가 다른 학생의 제출물과 정답 파일,
  명단 파일에 접근하고 수정할 수 있다. (F02)
- **세 환경은 격리가 아예 없다.** Windows·Linux·WSL 모드는 신뢰할 수 없는 학생 코드를
  조교 계정 권한으로 호스트에서 그대로 실행한다. 보호 장치는 10초 제한과 출력 읽기 상한뿐이다. (F03)
- **출력량에 상한이 없다.** 무한 출력 코드는 제한 시간 동안 임시 디스크를 채운다.
  실측에서 한 프로세스가 10초 안에 5.4 GiB를 기록했다. 코드 주석은 1 MB 제한이 있다고 적었지만
  그 값은 읽는 양에만 적용된다. (A3)
- **제한 시간이 지나도 학생 프로세스가 살아남는다.** 종료 신호는 컨테이너 클라이언트만 끝내므로
  컨테이너 안의 프로그램은 계속 돌아간다. 채점을 반복하면 좀비 프로세스가 쌓인다. (F09)

## 6. 잘 되어 있는 점

- **프로세스 실행 방식.** 출력을 파이프가 아닌 임시 파일로 받아 제한 시간을 거는 구조라
  출력이 많을 때 생기는 교착이 원천적으로 없다. 실측에서 5.4 GiB를 뱉는 프로그램에도 정확히 10초에 끊겼다.
- **줄바꿈 정규화.** 출력 비교 전에 줄바꿈을 통일하고 테스트케이스도 텍스트 모드로 읽는다.
  Windows와 리눅스가 섞인 환경에서 가장 흔한 오채점 원인 하나가 막혀 있다.
- **계층 분리.** 실행기가 화면 요소에 의존하지 않아 화면 없이 불러 검증할 수 있다.
  회귀 테스트를 붙이기 쉬운 형태라는 점이 실질적인 자산이다.
- **정답을 직접 실행해 만드는 케이스 생성.** 기대 출력을 손으로 적는 대신 정답 코드를 실제로 돌려 만들고,
  그 실행에 채점기와 같은 실행기를 재사용한다.
- **컨테이너를 기본값으로.** 격리를 지향한 방향 자체는 옳고 이미지도 최소한으로 유지되어 있다.
  컨테이너 쪽은 한글 출력 인코딩 문제에서도 자유롭다.
- **실사용에서 나온 최근 개선.** 숨김 폴더 제외, 숫자 기준 정렬, 빈 학생 폴더 명시,
  코드 미리보기 분리, 수동 실행 인자 입력. 모두 조교가 화면 앞에서 겪는 불편을 정확히 겨냥했다.

## 7. 고칠 순서

1. **개인정보를 저장소에서 분리** (F01). 명단과 데이터베이스 파일을 추적에서 빼고 무시 규칙을 추가한다.
   이미 원격에 올라간 이력 정리는 별도 판단이 필요하니, 우선 새 커밋에 더 들어가지 않게 막는 것이 먼저다.

## 9. 검증 방법

여덟 관점의 분석 에이전트가 소스 전체와 저장소 데이터를 읽어 133건을 보고했고,
같은 원인을 가리키는 항목을 67건으로 병합했다. 각 결함에 독립 검증자를 붙여 반박을 시도하게 하고,
과반이 반박하면 폐기했다. 검증자는 코드 정합성과 재현 가능성을 나누어 맡았고,
가능한 경우 격리된 임시 디렉터리에서 실제로 실행해 확인했다.
학생 저장소를 변경하는 명령은 쓰지 않았다.

### 반박되어 폐기한 주장 2건

- **Windows 모드 C 컴파일이 와일드카드 확장에 실패한다.**
  인용부호로 감싼 와일드카드를 MinGW GCC 13.1.0으로 실제 실행한 결과 정상 컴파일되었고,
  공백이 포함된 경로에서도 두 파일이 모두 링크되었다. 컴파일러가 자체적으로 확장한다.
- **동기화 중 창을 닫으면 스레드 파괴로 비정상 종료된다.**
  실제 화면을 띄워 작업 중 창을 닫는 실험을 반복했으나 매번 정상 종료되었다.
  동기화 중에는 로그 창이 따로 열려 있어 주 창만 닫아도 앱이 계속 살아 있다.

### 아직 다루지 않은 영역

성적 산출과 기록 계층 전체, 테스트케이스 자체의 품질 검증 절차, 제출 기한 판정과 유사도 검사,
개인정보 보관 기간과 정리 정책, 여러 조교가 같은 호스트를 공유할 때의 충돌.
저장소를 clone 하면서도 커밋 시각과 이력을 전혀 읽지 않아, git이 주는 가장 유용한 정보를 버리고 있다.
